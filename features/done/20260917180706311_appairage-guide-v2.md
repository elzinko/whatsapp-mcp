## En clair

Aujourd'hui, pour appairer WhatsApp il faut lancer `npm run pair` **à la main dans un
terminal**. Le but : le faire **depuis un chat ou Claude Code**, sans terminal. Deux
obstacles, découverts en réel le 2026-09-17 : le chemin « code d'appairage » plante
(`requestPairingCode` appelé trop tôt → `Connection Closed`), et le QR ne sort que dans
les **logs du serveur** (stderr), donc une conversation ne peut pas l'afficher. Cette fiche
répare le premier et **expose le QR/code dans la réponse d'outil**.

Suite de [fiche 20260916130039008](20260916130039008_appairage-whatsapp-guide.md) (#40).

## Contexte / Problème

- **Bug confirmé en réel** : `WhatsAppClient.start(phoneNumber)` appelle `requestPairingCode`
  **synchronement juste après `makeWASocket`**, avant que la connexion WS soit prête →
  `Impossible d'obtenir un code d'appairage : Connection Closed`. Le mock Baileys des tests
  ne l'avait pas attrapé — Codex l'avait pointé comme « à valider en réel » (P2b de #40).
- Le QR n'est écrit que sur **stderr**. Une conversation (chat/Code) ne peut donc pas
  l'afficher : il faut lire les logs ou lancer `npm run pair` au terminal.
- Résultat : l'appairage guidé « au premier appel » ne se conclut pas depuis une surface —
  d'où la question de l'utilisateur : « pourquoi devoir lancer `npm run pair` moi-même ? ».

## Proposition

1. **Réparer le timing de `requestPairingCode`** : ne plus l'appeler synchronement après
   `makeWASocket`. L'appeler quand Baileys est prêt — dans le handler `connection.update`,
   sur l'event `qr`, compte non enregistré, numéro fourni, **une seule fois** — pour
   demander le code au lieu d'afficher le QR.
2. **Exposer le QR/code dans la réponse d'outil** : `whatsapp_pair` renvoie en TEXTE, sans
   appairage, soit le **code** (voie 1), soit le **QR en art ASCII** (depuis `this.lastQR`,
   rendu par `qrcode-terminal`). Une conversation ou Claude Code l'affiche alors sans
   terminal.

Reste un geste humain (ADR-0005). **Ne résout pas** la collision multi-surfaces (verrou
`auth/`) — ça, c'est le démon ([fiche 0005](../0005-demon-frontends-mcp.md)).

## Critères d'acceptation

- [ ] `requestPairingCode` n'est plus appelé avant que la connexion soit prête ; le chemin
      code ne renvoie plus « Connection Closed » (validé en réel).
- [ ] `whatsapp_pair`, sans appairage, renvoie dans sa réponse d'outil soit le **code**
      (voie 1), soit le **QR en art ASCII** (voie QR) — affichable en chat/Code sans terminal.
- [ ] Le QR exposé vient de `this.lastQR` (le même que les logs), rendu en ASCII ; **jamais
      sur stdout** (réservé au JSON-RPC).
- [ ] Aucune régression : voie 2 (`npm run pair`), garde `nothingPairedYet`, invariant
      lecture seule, refus qui guident.
- [ ] Le vrai appairage (code/QR saisi côté téléphone) reste **manuel** (non-automatisable, ADR-0005).

## Comment vérifier

**Automatique (suite de tests) :**

1. Mock Baileys émettant un event `qr` → `requestPairingCode` appelé à CE moment (pas avant),
   une seule fois, seulement si numéro fourni + non enregistré.
2. `whatsapp_pair` avec `lastQR` posé → la réponse contient le QR ASCII ; avec numéro +
   élicitation → contient le code. Jamais rien sur stdout.

**Manuel (dernier mètre, une fois) :**

3. Depuis un chat/Code, sans appairage : appeler `whatsapp_pair` → voir le **code** ou le
   **QR** dans la réponse → le saisir/scanner sur le téléphone → `whatsapp_status` passe à
   `connected`.

## Faisabilité (2026-09-17)

- `this.lastQR` contient déjà le QR brut (posé à l'event `qr`, `src/whatsapp.js`) ;
  `qrcode-terminal` est déjà importé et sait le rendre en ASCII. Exposer = rendre `lastQR`
  et le mettre dans la réponse d'outil.
- Le fix de timing = déplacer l'appel `requestPairingCode` dans le handler `connection.update`
  (branche `qr`), gardé « numéro fourni + non enregistré + pas déjà demandé ».
- **Validation réelle obligatoire** : le mock ne rejoue pas le vrai WebSocket Baileys — le
  chemin code se valide à la main, comme le QR.
