**En clair.** Une fois le démon en place, le serveur MCP que chaque client lance devient
**mince**. Il garde les mêmes outils WhatsApp, mais chaque appel part vers le démon par la
socket, plus jamais vers WhatsApp. Le geste humain (Touch ID) reste ici, au plus près du client.
Résultat visé : Claude Desktop et N sessions Code tournent ensemble, sans se battre pour la
connexion. Deuxième pièce de l'épic [0005](0005-demon-frontends-mcp.md), après le démon.

## Contexte / Problème

Aujourd'hui, `src/index.js` **est** le serveur complet — Baileys inclus. Le lancer N fois, c'est
ouvrir N connexions sur le même `auth/` : la guerre de sessions et le 440
([épic parent](20260902223310355_acces-whatsapp-par-session.md), cause n°2).

Deux contraintes cadrent la réécriture :

- **Le frontend ne doit plus tenir WhatsApp.** Il ne connaît que la socket du démon
  (fiche [20260917211902097](20260917211902097_demon-tient-whatsapp.md)).
- **L'élicitation reste au frontend.** C'est le client qui a la surface pour présenter Touch ID.
  Déporter le consentement dans le démon l'éloignerait de la personne.

## Proposition

Réécrire `index.js` en **client mince** du démon :

- mêmes définitions d'outils — `whatsapp_status`, `list_groups`, `grant_channel`,
  `session_open` / `session_close`, `get_recent_messages`, `whatsapp_pair`, `whatsapp_help` ;
- mais chaque handler **appelle le démon** via le contrat NDJSON de la fiche socle ;
- `ensure_daemon_running()` au démarrage du frontend ;
- l'élicitation / Touch ID (`consent.js`, `touchid.js`, `strongauth.js`) **restent** dans le
  frontend : il ouvre le périmètre par un geste humain, puis le transmet au démon déjà consenti ;
- les **profils par projet** ([0004](done/0004-profils-par-projet.md)) deviennent des **scopes de
  frontend** : le frontend lit `WHATSAPP_PROFILE` et le passe au démon comme borne ;
- l'**appairage guidé** ([fiche 20260916130039008](done/20260916130039008_appairage-whatsapp-guide.md)) :
  le frontend **propose** la connexion, le démon l'exécute.

## Critères d'acceptation

- [ ] Claude Desktop + plusieurs sessions Code simultanées : **zéro 440**.
- [ ] Le frontend **ne touche jamais WhatsApp** : il ne connaît que la socket du démon.
- [ ] Les outils MCP existants répondent à l'identique (statut, groupes, grant, session,
      messages récents, appairage, aide).
- [ ] L'élicitation / Touch ID s'exécute **côté frontend** ; le démon reçoit un périmètre déjà
      consenti.
- [ ] Le profil du projet borne ce que ce frontend peut demander ([0004](done/0004-profils-par-projet.md)
      respecté).
- [ ] **Fermer un client ne coupe ni la connexion ni la capture** — le démon survit.

## Comment vérifier

- `npm test` — contrat frontend↔démon mocké (chaque outil appelle le bon verbe, transmet le
  périmètre consenti, ne parle jamais à Baileys).
- Manuel : deux clients réels (Desktop + Code) en parallèle, chacun lit dans son périmètre,
  **aucun 440** dans les logs.
- Manuel : fermer la session Code → la capture continue (constaté via l'archive), le statut
  répond toujours depuis Desktop.

## Notes

- Dépend de la fiche socle [20260917211902097](20260917211902097_demon-tient-whatsapp.md)
  (le contrat socket).
- L'élicitation signée v2 ([0007](0007-elicitation-signee-touch-id.md)) reste **optionnelle** :
  elle ne se déclenche que si le frontend devient non fiable ou passe par le réseau — pas le cas
  ici, tout est loopback.
- Le serveur ne configure jamais le client
  ([ADR-0005 / fiche 0012](done/0012-adr-serveur-ne-configure-pas-le-client.md)) : le branchement
  reste `npm run install:client`, lancé par l'humain.
