**En clair.** Le démon est **livré** (#44, le 20/09) : un seul process tient WhatsApp derrière une
socket locale. Reste l'autre moitié : rendre **mince** le serveur MCP que chaque client lance. Il
garde les mêmes outils, mais chaque appel part vers le démon par la socket, plus jamais vers
WhatsApp. Le geste humain (Touch ID) reste ici, au plus près du client. Résultat visé : Claude
Desktop et N sessions Code tournent ensemble, sans se battre pour la connexion. Deuxième pièce de
l'épic [0005](0005-demon-frontends-mcp.md), après le démon.

## Pourquoi ça compte (valeur)

Le démon seul ne sert à rien : **aucun client ne lui parle encore**. C'est cette fiche qui
transforme le socle en bénéfice réel. Tant qu'elle n'est pas livrée :

- le vrai multi-clients (Desktop + N Code, **zéro 440**) n'existe pas — c'était la promesse n°2 de
  l'épic parent ;
- en pratique la capture ne survit pas à la fermeture d'un client, puisque le client reste le
  serveur monolithe ;
- le démon tourne à vide, sans consommateur.

Livrer cette fiche **clôt l'épic 0005** (l'admin de monitoring est optionnel) et fait avancer le
fil directeur « un chat Desktop qui marche ».

## Contexte / Problème

Aujourd'hui, `src/index.js` **est** le serveur complet — Baileys inclus : il compose
`WhatsAppClient`, prend le verrou `auth/`, ouvre la connexion. Le lancer N fois, c'est ouvrir N
connexions sur le même `auth/` : la guerre de sessions et le 440
([épic parent](20260902223310355_acces-whatsapp-par-session.md), cause n°2).

Deux contraintes cadrent la réécriture :

- **Le frontend ne doit plus tenir WhatsApp.** Il ne connaît que la socket du démon
  ([ADR-0008](../docs/adr/0008-demon-unique-socket-locale.md)).
- **L'élicitation reste au frontend.** C'est le client qui a la surface pour présenter Touch ID.
  Déporter le consentement dans le démon l'éloignerait de la personne (ADR-0008 §3).

## État des lieux — ce que #44 a livré, et le manque (grooming 2026-09-29)

Le démon a shippé **plus** que la plomberie : le client est déjà écrit.

**Déjà en place** (à réutiliser, pas à réécrire) :

- `src/daemon-client.js` : `request(socketPath, req)` (une requête NDJSON → une réponse) **et**
  `ensureDaemonRunning()` (ping → spawn détaché → polling borné → log). Le critère
  « `ensure_daemon_running` au démarrage » est donc **déjà couvert**.
- `src/daemon-protocol.js` : le contrat, **5 verbes** — `status`, `list_groups`, `recent`,
  `session_open`, `session_close`. Le périmètre (session ∩ grant ∩ plafond) est appliqué **côté
  démon**.
- `src/daemon-secret.js` : le secret de socket (garde-fou anti-parasite, ADR-0008 §5).

**Le manque — c'est le cœur de cette fiche.** Le frontend expose **9 outils** ; le contrat n'en
couvre que **5**. Trois outils **mutants n'ont aucun verbe** :

| Outil MCP (index.js) | Verbe démon | Ce qu'il faut faire |
|---|---|---|
| `whatsapp_help` | — (texte local) | rien : reste 100 % frontend |
| `whatsapp_status` | `status` (partiel) | le frontend compose autour (`grantConsent`, `version`) ; le démon doit exposer `registered` (état appairé) |
| `list_groups` | `list_groups` ✓ | l'état « rien appairé » vient du `status` démon |
| `get_recent_messages` | `recent` ✓ | la résolution **nom → JID** reste au frontend (le démon exige un JID exact — noté dans `daemon.js`) |
| `session_open` | `session_open` ✓ | Touch ID au frontend, puis appel du verbe |
| `session_close` | `session_close` ✓ | direct |
| **`grant_channel`** | **absent** | **ajouter un verbe `grant`** — les grants vivent dans le démon |
| **`revoke_channel`** | **absent** | **ajouter un verbe `revoke`** |
| **`whatsapp_pair`** | **absent** | **ajouter un verbe d'appairage** — voir décision ci-dessous |

**Pourquoi l'appairage n'est pas optionnel.** Le démon tient le **verrou `auth/`**. Un
`npm run pair` lancé à côté trouverait le verrou pris et sortirait (ADR-0008 §4). Une fois le
frontend mince, **l'appairage doit passer par le démon** : plus aucun autre process ne peut toucher
`auth/`. C'est une conséquence forcée du verrou, pas un confort.

## Proposition

Réécrire `index.js` en **client mince** du démon, **et étendre le contrat** pour les mutations qui
n'ont pas de verbe.

1. **Câbler les 5 verbes existants.** Chaque handler de lecture/session appelle
   `daemon-client.request()` au lieu de `wa.*` : `whatsapp_status`, `list_groups`,
   `get_recent_messages`, `session_open`, `session_close`. `ensureDaemonRunning()` au démarrage.
2. **Étendre le contrat NDJSON** (`daemon-protocol.js` + backend `daemon.js`) avec les verbes
   manquants : `grant`, `revoke`, et l'appairage (`pair` + récupération du code/QR). Même patron que
   `session_open` : le frontend fait le **geste humain** (Touch ID / élicitation), **puis** demande
   au démon d'exécuter la mutation déjà consentie (ADR-0008 §5).
3. **Ce qui reste au frontend** (ne migre pas dans le démon) :
   - l'**élicitation / Touch ID** (`consent.js`, `touchid.js`, `strongauth.js`) — le geste ;
   - la **résolution nom → JID** (`wa._resolveToJid`) — le démon exige un JID exact ; le frontend
     résout à partir de la liste des groupes obtenue du démon (`list_groups`) ;
   - le **profil par projet** ([0004](done/0004-profils-par-projet.md)) : le démon capte
     **grant ∩ plafond** sans profil (il est partagé par tous les frontends) ; c'est **le frontend**
     qui applique le profil comme borne des canaux qu'il demande (confirmé par le commentaire de
     `daemon.js`).
4. **Transition** : démon et frontend legacy partagent le verrou `auth/` (ADR-0008 §4), donc restent
   mutuellement exclusifs — on bascule d'un bloc, pas de cohabitation.

## Décisions de conception (à tenir)

- **Les mutations passent par de nouveaux verbes, pas par un fichier partagé.** Tentant : laisser le
  frontend écrire `settings.json` (grants) en direct et le démon relire. Rejeté : course entre deux
  process sur le même fichier, et surtout **l'appairage est impossible par fichier** (il faut Baileys
  vivant, que seul le démon tient). Un verbe = un point d'entrée unique, testable à froid, cohérent
  avec « le démon détient les grants et Baileys » (ADR-0008 §1).
- **Appairage inclus dans cette fiche (défaut retenu).** Le verrou force l'appairage à passer par le
  démon dès que le frontend est mince ; le laisser dehors bloquerait tout poste non appairé.
  Alternative si le lot paraît trop gros : livrer d'abord lecture + grant/revoke, et garder un interim
  documenté « arrêter le démon, `npm run pair`, relancer ». **À confirmer par le PO** — sinon on
  splitte l'appairage en sous-fiche.
- **Le consentement ne se déporte jamais.** Le démon ne présente aucun prompt ; il fait confiance au
  frontend authentifié-par-secret qui affirme qu'un consentement a eu lieu (ADR-0008 §5). Le frontend
  reste le seul à parler à l'humain.

## Critères d'acceptation

- [ ] Claude Desktop + plusieurs sessions Code simultanées : **zéro 440** dans les logs.
- [ ] Le frontend **ne touche jamais WhatsApp/Baileys** : `src/index.js` n'importe plus
      `WhatsAppClient` (grep d'import = 0) ; il ne connaît que la socket du démon.
- [ ] Les **9 outils MCP** répondent à l'identique (aide, appairage, statut, groupes, grant, revoke,
      session open/close, messages récents) — mêmes entrées, mêmes sorties qu'aujourd'hui.
- [ ] Le contrat NDJSON est **étendu** : verbes `grant`, `revoke` et appairage ajoutés, chacun
      appliquant le périmètre **côté démon** (grant ⊆ plafond) et journalisé au besoin.
- [ ] L'élicitation / Touch ID s'exécute **côté frontend** ; le démon reçoit une mutation déjà
      consentie (jamais de prompt côté démon).
- [ ] La **résolution nom → JID** se fait côté frontend, à partir de la liste obtenue du démon
      (aucun accès Baileys dans le frontend).
- [ ] Le **profil du projet** borne les canaux que ce frontend demande
      ([0004](done/0004-profils-par-projet.md) respecté), alors que le démon capte sans profil.
- [ ] **Fermer un client ne coupe ni la connexion ni la capture** — le démon survit (déjà vrai côté
      démon ; à constater de bout en bout).
- [ ] L'appairage fonctionne **via le démon** (le verrou `auth/` interdit un process d'appairage
      séparé) — ou, si le PO splitte, l'interim documenté est en place.

## Comment vérifier

- `npm test` — contrat frontend↔démon **mocké** : chaque outil appelle le bon verbe, transmet le
  périmètre déjà consenti, et **n'importe jamais Baileys** (grep d'import dans `index.js` = 0). Les
  nouveaux verbes (`grant`, `revoke`, appairage) testés à froid dans `test/daemon-protocol.js` avec un
  backend factice, comme les 5 existants.
- Manuel : deux clients réels (Desktop + Code) en parallèle, chacun lit dans son périmètre, **aucun
  440** dans les logs.
- Manuel : fermer la session Code → la capture continue (constaté via l'archive), le statut répond
  toujours depuis Desktop.
- Manuel : depuis un poste **non appairé**, `whatsapp_pair` guide l'appairage **sans** lancer de
  process concurrent sur `auth/`.
